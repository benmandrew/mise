# Testing

Run the tests in the Nix shell (`nix develop`, or direnv with `.envrc`), so that they use the Ninja, Python and compiler pinned by `flake.lock`.

- `scripts/check.sh` is the acceptance gate: it builds everything, rejects `sorry` and `admit`, and checks the axioms of every headline theorem. The Lean tests in `test/MiseTest/` are `#guard` checks that run during the build.
- `test/stage3-diff.sh` compares the parser and evaluation models with real Ninja on 100 random manifests, and checks that both reject 17 malformed ones.
- **Parser fuzzer.** `test/parser-fuzz.sh [text|gen] [SECONDS] [-- LIBFUZZER_ARGS]` is a *differential fuzzer* for the parser model, and runs for 60 seconds by default. It needs clang with libFuzzer: on Linux run it in `nix develop .#fuzz`; on macOS the default shell's clang has it. It builds a libFuzzer binary that links Ninja's own manifest parser, from the source of the flake's pinned Ninja (`NINJA_RELEASE` picks the release, 1.13.2 by default), with the Lean model in `test/MiseTest/ParseFuzz.lean`, compiled from its C in `.lake/build/ir`. Both are instrumented for coverage and run in one process. When the model's `parse` accepts a manifest, Ninja's `ManifestParser`, in its test mode with no files, must accept it too. It must also read the same edges (rule, explicit and implicit outputs, explicit, implicit and order-only inputs, validations), the same evaluated `command`, `description`, `depfile`, `deps` and `restat` on each non-phony edge, and the same defaults. Both sides print these fields as `KEY LEN:VALUE` lines, with LEN in bytes. An input the model rejects is not checked, because Ninja accepts more than the subset. Edges whose rule variables form a cycle are not compared, because Ninja exits when it evaluates them and the model cuts the recursion with fuel. Inputs whose `ninja_required_version` would make Ninja warn or exit are skipped.

  In `text` mode libFuzzer mutates raw manifest text. It starts from 200 manifests of the `difftest` generator behind `test/stage3-diff.sh` and its negative cases, with a dictionary of Ninja tokens in `test/parser-fuzz.dict`. In `gen` mode the input bytes are the *choice sequence* for `genManifest`, the `difftest` generator, through the byte-driven generation under `test/fuzz.sh` below. So every input is a manifest the model accepts, and a mutation changes individual generator choices. Two runs of `test/parser-fuzz.sh` on an M-series Mac tested 8,816 and 10,463 inputs a second on one core. *AddressSanitizer* (ASan) is on by default except on macOS, where the ASan of nixpkgs' clang 21 hangs at start-up; `MISE_FUZZ_ASAN=1` or `0` overrides the default. Each mode keeps its corpus in `test/out/parser-fuzz/corpus-text` or `corpus-gen`, failing inputs go to `test/out/parser-fuzz/crash/`, and `test/parser-fuzz.sh repro text|gen FILE` replays one.

  The fuzzer found four places where the model accepted a manifest that Ninja rejects or reads differently, and all four are now fixed in the model. The first is a nonempty file whose last line has no newline. The second is a NUL byte in a comment, which Ninja's lexer reads as the end of the input. The third is an edge variable `pool` that names no declared pool. `pool` and `dyndep` are now `parseTimeKeys`, rejected as top-level or edge variables and reserved in the DSL, so a TOML parameter can no longer take either name. The fourth is a phony edge that lists its own output as an input, which Ninja drops; an edge may no longer list its own outputs as inputs. `Mise/Syntax/NOTES.md` records all four.
- `test/stage4-hello.sh` builds and runs `examples/hello-c`, and checks that the DSL's commands match `ninja -t commands`.
- `test/sugar.sh` tests the `mise.toml` conveniences against real Ninja on a small C program. A `source-globs` pattern finds the sources, a `foreach` build compiles them with depfiles, and a link written before it reads every object through a `%` input. It checks that an alias builds its targets and nothing else, that a header edit rebuilds only its reader, that a new source file is compiled and linked by the next `mise build` and a deleted one is unlinked, and that the DSL's commands match `ninja -t commands`.
- `test/wrap-outputs.sh` tests the command wrapper on an edge without `restat`, with two explicit outputs and an implicit one whose name needs quoting. A command that exits 0 without writing an output fails the build with `mise: out/b.txt was not written`, leaves every old output with its mtime and no `.mise-old` files, and runs no dependent; the next build retries the edge with no edit in between. A command that fails after a partial write does the same, a first build that fails leaves no outputs and removes a stale `.mise-old` file, and the build after the command is fixed recovers. With `wrap = false` the same command lets the build succeed and leaves Ninja with work on every later build.
- `test/restat-cmp.sh` tests the wrapper's `cmp` on a `restat` edge with two explicit outputs and an implicit one whose name needs quoting. An edit that leaves the outputs the same reruns only that edge and keeps every mtime, and an edit to one output reruns only its dependent. A failing command and a missing output fail the build and leave the old outputs, their mtimes and no `.mise-old` files, and the next build recovers. The commands always write, so the early cutoff comes from the wrapper; with `wrap = false` the test fails at the first cutoff check.
- `test/stage6-props.sh` runs sequences of edits on each example, building after each edit with a random `-j` level. The edit kinds follow a de Bruijn sequence of order 3, so every ordered triple of edit kinds occurs in some sequence; the edits' values are random. `--order 2` covers every pair instead, and `--random N` runs N sequences of random edits. After every build it compares the products with a clean build byte for byte, and checks that `ninja -n` has no work and `ninja -t missingdeps` finds nothing. After a comment-only edit to `config.in` it checks that only the generator ran. Sequences run in parallel, one worker per core by default (`--workers`), and each has its own seed, so the results do not depend on the number of workers. Each manifest is generated once per `cflags` value, and compiles go through ccache (`--no-ccache` turns it off); a cache hit returns the same object a compile would, so a skipped rebuild still leaves a stale product. With seed 1 it ran 96 edits on `hello-c` and 1,500 on `gen-header`, covering all 64 and all 1,000 triples, in 126 seconds on 8 cores with a warm cache, and every check passed. For comparison, `--random 200` takes 65 seconds and covers all 64 and 265 of the 1,000 triples; `--order 2` takes 30 seconds and covers every pair.
- `test/fuzz.sh [N] [SEED]` tests the Ninja model on random graphs. `lake exe fuzzgen` (`test/MiseTest/Fuzz.lean`) generates N graphs, 500 by default, with static, depfile and `restat` rules, implicit inputs and outputs, order-only inputs, edge variables and two aliases. With `Rng.ofBytes` (`test/MiseTest/Rng.lean`) the generators draw their choices from a byte string in place of a seed, each `rand n` reading the next one to four bytes big-endian modulo `n` and zeros past the end, so every byte string gives a valid case and the empty string gives the case of all first choices; `lake exe fuzzgen bytes IN OUT [OPTS]` and `lake exe difftest bytes FILE DIR` generate one case from a byte file. A depfile edge has one explicit output and up to two implicit ones, so Ninja reads its deps from the first of several outputs. Every edge runs one helper, `test/fz.c`, which hashes what it reads and follows `include` lines for depfile rules; `Fuzz.lean` gives the model the same semantics. Edges without `restat` go through the DSL's command wrapper. On half the `restat` edges the helper itself leaves unchanged outputs alone (`wrap = false`); on the other half it always writes, and the wrapper's `cmp` decides. Each graph comes with a sequence of steps. A step makes some edits: change a source, add a comment, add or remove an `include` line, change an edge's command, rewrite a source with the same contents (only its mtime changes), delete a product, delete `.ninja_log` or `.ninja_deps`, remove an edge that nothing reads (its outputs stay on disk), add an edge, either a new one or one removed earlier, or *age* a product (set its mtime to one second after the epoch, as restoring it from a backup would). The step then builds in one of three ways: every edge; only some targets (`ninja TARGET...`), which the model predicts by building the edges the targets need; or with one edge's command failing, chosen by `FZ_FAIL`. Every build runs under `-k 0`, where Ninja builds everything that does not depend on a failure, except a build that stops at the failure, which runs under the default `-k 1`. Which edges finish before a stop depends on Ninja's scheduling, so the driver hands them to `fuzzgen expect`, which checks that each was dirty on its turn and read only up-to-date inputs, and recomputes the later steps from that state. A failed run of a wrapped command leaves the state as it was (`Mise.Headline.wrapped_run`), so a failed build is modelled as steps of the edges that finished; `Mise/Model/NOTES.md` lists what that leaves out. `test/fuzz.py` replays the steps against real Ninja with `-j` chosen at random from 1, 2, 8 and 64, or from 1 and 2 for a build that stops, since with many jobs in flight Ninja usually finishes every edge that does not depend on the failure. After each build it checks that exactly the model's edges ran, each once, that the runs form a schedule (below), that the failing edge was tried and Ninja failed exactly when the model says, that every output the case has had holds the model's contents or is missing when the model says so, and that `ninja -n` has no work (for the targets, after a partial build; not after a failure); after the last step, `ninja -t missingdeps` must find nothing. The run-set check also tests minimality, which a clean-build comparison cannot see. Touching a source, deleting both logs, and partial and failed builds stay within `Reach`, so the theorems cover them. Deleting one log and removing an edge keep `Inv`, though no theorem states it. Deleting a product and adding an edge leave what the theorems cover, so there the harness tests only the model's dirtiness rule. With seed 1 the 500 cases have 3,313 steps and all pass in 74 seconds on 8 cores. Of the 2,813 builds after the first, 1,861 build everything (1,123 rebuild part of the graph, 442 all of it and 296 nothing), 452 build some targets, 231 run under `-k 0` (129 where the failing edge was dirty and tried) and 269 stop at a failure; 435 age at least one product. At cc432f5, before the schedule check and the `cmp` wrapper, 132 of 251 stopped builds tried the failing edge, and 36 of those left unstarted an edge that `-k 0` would have run. The steps hold 589 added edges, 434 removed edges, 447 deleted products, 469 aged products, 435 touches, 219 `.ninja_log` and 200 `.ninja_deps` deletions, and 2,241 edits of the earlier kinds; 820 of the 1,246 depfile edges have implicit outputs. Two broken helpers show what the checks catch: at 8af16e6, one that never keeps a `restat` output failed 77 cases (64 at 59b14fb, before the new steps, and 128 before half the `restat` edges moved to the wrapper), and one whose depfile leaves out included files failed 169 (252 at 59b14fb). A failing case is shrunk: the driver drops steps, edges, edits, inputs, outputs, includes and sources one at a time, turns partial and failed builds into full builds, has `fuzzgen expect` recompute the model's steps, and keeps each change that fails the same check. `--fz PATH` runs a given helper binary in place of `test/fz.c`. With the `restat` mutant, the first three failures (7 to 10 edges and 7 to 12 edits) shrank to 2 to 4 edges and 1 or 2 edits, in 104 to 157 trials and 26 to 48 seconds. The result goes to `test/out/fuzz/shrunk/<i>.json`, and `test/fuzz.py test/out/fuzz/shrunk <i>` replays it. `test/fuzz.sh --opts absent` tests the wrapper's failure path. A quarter of the edges get a wrapped command (`fz` mode `x`) that leaves out each output whose hash is a multiple of 3. The wrapper fails such a run with `mise: OUT was not written` and puts the old outputs back with their mtimes, so in the model the run changes nothing (`natFail` in `Fuzz.lean`, after `Mise.Headline.wrapped_run`). The edge stays dirty, Ninja retries it in the next build, and no edge that reads its outputs runs. These cases keep every check and have fail and stop steps like the others; a build stops at the first failure, from `FZ_FAIL` or from a left-out output. With seed 1, 200 cases (1,325 steps) pass in 25 seconds on 8 cores, and 494 of the 1,125 builds after the first fail on a left-out output. `--opts absent,nowrap` tests a known difference from the model instead: half the `restat` edges get the same command outside the wrapper (`wrap = false`), and the model gives a left-out output the empty contents a missing file reads as. Ninja then reruns those edges in every build, so these cases fail the run-set and `ninja -n` checks by design (40 of 60 with seed 1 at 8af16e6, all on `ninja -n`). Ninja would also try a failing edge, and finish edges before a stop, that the model finds clean, so under `nowrap` no edge is made to fail. Such case files say `"missingOk": true`, which turns on `--missing-ok`. It allows exactly that difference: an edge with a missing output may also run, and a second build in place of `ninja -n` may run only such edges and must leave the same contents. The schedule check runs on both builds. With it, 50 cases (336 steps) pass in 10 seconds on 8 cores. With seed 2, 5 of 100 cases fail the run-set check, the same 5 at 8af16e6: in each, Ninja skips an edge that the model runs. In the shrunk case 42 that edge reads an output its `x` producer left out. The wrapper rules this out, so it stays a difference for unwrapped commands only. See `Mise/Model/NOTES.md` for both differences.
- **In-process build fuzzer.** `fuzz/build/build.sh [libfuzzer|afl|standalone]` builds one binary and prints its path. Run it inside `nix develop .#fuzz`, the flake's `fuzz` shell, which adds clang, AFL++ on Linux and `NINJA_SRC`. The binary links the build logic of Ninja 1.13.2 (`State`, `ManifestParser`, `BuildLog`, `DepsLog`, `Builder`) with the Lean model and the case generator of `test/fuzz.sh` (`MiseTest.Fuzz`). Commands run against an *in-memory file system* whose clock ticks once per edit and twice per command, so no two mtimes tie. The command runner does what `test/fz.c` and the DSL's wrapper do, and each command reads its inputs when it starts and writes its outputs when it finishes. `.ninja_log` and `.ninja_deps` are real files in a temporary directory, so Ninja's own load, append and recompaction run. The low bit of an input's first byte turns on `Opts.absent`. The generator reads the rest from the front as its choice sequence (`Rng.ofBytes`). The harness reads its scheduling choices backwards from the end, which are `-j` for each step (1, 2, 8 or 64) and which command in flight finishes next. Both stay put when the fuzzer inserts bytes in the middle.

  The harness checks what `test/fuzz.py` checks, except the schedule timings and `-t missingdeps`. These checks are the edges that ran, whether the failing edge was tried, the build's exit status, every output's contents, and that `ninja -n` has no work after a successful build. On a mismatch it writes the case to `test/out/fuzz/inproc/<n>.json` (or `$MISE_FUZZ_OUT`) and aborts, and `test/fuzz.py test/out/fuzz/inproc <n>` replays the case against real Ninja. In standalone mode, `BIN N [SEED]` runs N inputs of 4,096 pseudo-random bytes and `BIN FILE...` replays files. With N = 500, the 500 cases (3,233 steps) ran in 9.1 seconds, 55 cases a second and about 65 times the step rate of `test/fuzz.sh` against real Ninja. libFuzzer ran 257 inputs a second on short inputs and found 671 new coverage units in 2 minutes, with no mismatches. `fuzz/build/mutants.py [--cases N]` runs the mutants of `test/mutants.py` through the standalone harness with the model's self-checks off (`MISE_FUZZ_NO_SELF_CHECK`). It kills every mutant except `log-old-time`, which is equivalent, in about 12 seconds per mutant. The harness does not cover real mtime granularity and ties, real processes, the real `sh` wrapper and `cmp`, overlap in time, `mise gen`, `-t missingdeps`, or sandbox and trace confinement. ASan from nixpkgs hangs at start-up on macOS.
- The schedule check in `test/fuzz.py` tests the assumption behind `parallel_equiv`: a parallel run has the effect of its commands in order of start time, each reading its inputs at the start and writing its outputs at the end, and Ninja's ordering makes that sequence a `Sched`. For every run, `fz` logs six `CLOCK_MONOTONIC_RAW` times (entry, first and last input read, first and last write, exit) and the files it read. Check (b) asks that the six times are in that order, so every read of a command comes before its first write. Check (a) asks that every run starts after each edge producing one of its inputs is done, where inputs are explicit, implicit and order-only inputs and the files the run read, so discovered deps count. A producer that ran is done when it exits, and one that did not run is done when its own producers are, the earliest point at which Ninja could find it clean. Check (a) gives the second conjunct of `Sched`, that no edge reads a later edge's outputs, for the edges sorted by start time; the driver also checks all three conjuncts on that order directly, and the first and third (no edge reads its own outputs, outputs are unique) hold for every emitted manifest by `sched_emit`. Because a producer has exited before a reader starts, two runs that overlap in time never read each other's outputs, so with (b) the parallel run has the effect of the sequence. Each command sleeps a random 0 to 20 ms after entry and again before writing (`--delay`, in microseconds, 0 to turn it off), because without the sleep `fz` exits before Ninja has spawned the next command. With seed 1, 983 of the 1,552 builds at `-j` above 1 that ran two or more edges ran edges at the same time, with 2,396 overlapping pairs and at most 5 runs at once, and every check passed; the counts vary between runs with the machine's load. At 59b14fb, before partial and failed builds, 1,197 of 1,854 such builds overlapped in one run, with 2,780 pairs and at most 5 at once, and 1,015 builds with 1,917 pairs in another; with `--delay 0` only 35 builds overlapped; and with `--delay 0`, a helper that logs its entry 1 s early failed 488 cases on check (a), and one that logs its last write before its first read failed all 500 on check (b). A run whose command fails through `FZ_FAIL` logs nothing, so it is a producer that did not run.
- `test/mutants.sh [--cases N] [--seed S] [--workers W] [MUTANT...]` checks that the random-graph harness catches a wrong model. Each mutant in `test/mutants.py` is one small edit to a definition in `Mise/Model/Basic.lean`. The script applies it to a copy of the tree in `test/out/mutants/tree`, so the real model never changes, and rebuilds only `fuzzgen`. That rebuild skips the proofs: `Basic.lean` holds definitions only, and `test/MiseTest/Fuzz.lean` imports it and none of `Sound.lean`, `Dsl.lean`, `Minimal.lean`, `Parallel.lean`, `Cmp.lean` or `Mise/Headline.lean`, so the proofs the mutant breaks are never compiled. For each mutant the script runs the generator twice. The first run keeps the generator's own checks (a second build runs nothing, a depfile edge reads only what it may) and records the first failure. The second run turns them off (`FUZZGEN_NO_SELF_CHECK=1`), and `test/fuzz.py --no-shrink` replays its cases against real Ninja and counts the failing cases by check. The unmutated model runs first and must pass. The table goes to `test/out/mutants/results.md`. A run writes the log entry and the deps entry together, and no edit then removed one without the other, so a depfile output with a log entry always had a deps entry. - `test/ninja-matrix.sh [--workers W] [--fuzz N] [--seed S] [RELEASE...]` runs the four shell harnesses above against several Ninja releases: `stage3-diff.sh`, `stage4-hello.sh`, `stage6-props.sh --order 2` and `fuzz.sh` with N cases (500 by default). With no RELEASE it runs the supported releases, 1.12.1 and 1.13.2. Ninja 1.10.2 and 1.11.1 are unsupported, for the failure below: the script first checks that each refuses an emitted manifest with "incompatible with build file ninja_required_version". `test/ninja-matrix.sh --refuse-only [RELEASE...]` runs only that check, for the named releases (by default the unsupported ones), and exits nonzero if one accepts the manifest or fails with another error. Named explicitly, an unsupported release still runs the harnesses, and is known to fail. It runs through a `ninja` shim in `test/out/matrix/<release>/shim/` that gives it a copy of `build.ninja` with the version binding lowered to that release. The flake builds each release from its upstream tag as the package `ninja-1_10_2`, `ninja-1_11_1`, `ninja-1_12_1` or `ninja-1_13_2`, without nixpkgs' patch to spawn `sh` from PATH; releases before 1.12 get the upstream fix that lets `configure.py` run on Python 3.13. The script runs in the default shell and puts each release first on PATH, so only Ninja changes. `nix develop .#ninja-1_10_2` (and so on) gives a shell with that release for running one harness by hand. Logs go to `test/out/matrix/<release>/`. Ninja 1.10.2 has no `-t missingdeps`, so on it `props.py` and `fuzz.py` skip that check and say so. These two failures are why the minimum is 1.12.1. Ninja 1.12.0 was not tested.
- `test/conf-sandbox.sh [N] [SEED]` checks trust-base item 2 on macOS. `test/confine.py` rewrites each `build.ninja` so that every command runs under `sandbox-exec` with its own profile, which kills the command when it reads the contents of a file it may not read or writes a file it may not write. Every command may read the toolchain (the Nix store, system libraries, random devices and a private `TMPDIR`) and its own outputs, which a `restat` command reads to decide whether to keep them. In the build directory a static command may also read its explicit and implicit inputs, and a depfile command may read what `Graph.DynOK` allows: any path no edge produces, and its own inputs, order-only ones included. A command may write only its outputs, its depfile, the temporary files clang renames onto its outputs, and its `TMPDIR`. The script builds each example through 9 and 21 states (the example's own files, then each edit kind of the property harness in turn and back again), 70 commands in all, and then runs the N random-graph cases (500 by default) with `fuzz.py --confine sandbox`. Every build passed; the random graphs took 164 seconds on 8 cores, against 74 without the sandbox. Three broken examples build without the sandbox and are killed under it: `hello-c` with `greet.h` no longer an implicit input of its compiles, which `ninja -t missingdeps` cannot see because the edge has no depfile; `gen-header` with `build/config.h` no longer an order-only input of `util.o`; and `hello-c` compiling with `-MMD` without declaring the depfile. For each, a third build refuses without killing and traces the refusals, which names the file (`./greet.h`, `build/config.h` and `build/main.d`). The sandbox does not confine metadata: a command may `stat` any path and list any directory in the build directory, since clang's include search stats paths that may not exist and Python lists its script's directory. Outside the build directory it is stricter than `Graph.DynOK`, which allows any path no edge produces. Commands must be simple commands (no shell operators), since the prefix applies to the first program only. A command in the DSL's wrapper is the exception: the prefix goes on the command inside the wrapper, so the command is confined exactly as it would be alone. Through the wrapper the three broken examples still fail with the command's status, 137 (SIGKILL). A sandboxed process cannot start a second sandbox (`sandbox_apply` fails with "Operation not permitted"), so the wrapper cannot run inside one around the command's. Instead the wrapper's `sh` runs outside any sandbox, and each `mv`, `rm` and `cmp` it starts runs under a profile of its own, which allows reads of the toolchain and reads and writes of the edge's outputs and their `OUT.mise-old` copies, and nothing else in the build directory. That profile refuses without killing, and the harness fails any build whose output shows a refusal. The `sh` runs only builtins (`set`, `for`, `[`, `echo` and `exit`), which test whether files exist and write to standard error. Linux has no `sandbox-exec`, so the script skips there.
- `test/conf-depfiles.sh [N] [SEED]` checks item 3. `test/trace.c` is a shared library that wraps `open`, `openat` and `fopen` and logs every file a process opens, with its resolved path; `confine.py` loads it into every command with `DYLD_INSERT_LIBRARIES` (`LD_PRELOAD` on Linux, which is untested). After each build, every file a depfile command read in the build directory must be an explicit or implicit input of its edge or a dependency Ninja recorded from its depfile (`ninja -t deps`), and every command's reads and writes must be ones the sandbox allows. Reads outside the build directory must be in the toolchain; they are not compared with the depfile, since `-MMD` leaves system headers out. On the examples, 70 commands ran; the 23 depfile compiles read 75 files in the build directory, all listed, and the commands read 3,770 toolchain files. Only the command inside the wrapper is traced, since the prefix goes on it alone, so the wrapper's `mv`, `rm` and `cmp` do not count as reads of the outputs or their `OUT.mise-old` copies. Ninja records no deps for a depfile command that fails, so such a command's reads are checked against the sandbox's rules only. With seed 1, `test/fuzz.sh --opts absent 50 1 -- --confine sandbox` and `-- --confine trace` both pass, so the wrapper's failure path runs confined. The 500 random-graph cases all passed, in 138 seconds. Two broken builds fail: `gen-header` with `-isystem build` in place of `-Ibuild`, which makes `build/config.h` a system header that `-MMD` leaves out of both depfiles, and a helper whose depfile drops the last file it read, which failed 432 of the 500 cases at 8af16e6, each on an unlisted read. The tracer misses some reads. macOS strips `DYLD_*` from protected programs (anything in `/bin` or `/usr/bin`), and the check fails a command that ran but left no trace. It does not see reads by the dynamic loader, through raw system calls, by a statically linked program, or through a descriptor inherited from another process, and it does not see metadata reads such as `stat`.
- `test/conf-determinism.sh` checks the determinism half of item 2. For each example and each of four `cflags` values it makes two clean builds in different directories, at least a second apart, with `-j1` and `-j8` and with different time zones and locales, and compares the products byte for byte. With `-O2 -Wall`, `-O0` and `-O1 -DMISE_FLAG=1` all 7 products are identical. With `-O0 -g` the objects embed the build directory, and they are identical once one directory's path is substituted for the other (the two names have the same length). The linked binaries embed the objects' paths, and differ also in `LC_UUID` and the ad hoc code signature, which the linker computes over the contents; with the path substituted and those two zeroed, they are identical. The helper `fz` of the random-graph harness is deterministic by construction, and `fuzz.sh` checks its outputs against the model.
- `test/toml-diff.sh [N] [SEED]` compares the `mise.toml` parser with Python's `tomllib`, which reads TOML 1.0. `test/toml_diff.py` writes N random documents of each of four kinds, 2,500 by default, and `lake exe tomljson` (`test/MiseTest/TomlJson.lean`) prints the Lean parser's value tree for each as canonical JSON, the same bytes as Python's `json.dumps(v, sort_keys=True, separators=(",", ":"))`. Subset documents use only what the parser reads: basic strings with every escape, raw and escaped Unicode up to U+10FFFF, literal strings, decimal integers with signs and underscores, booleans, arrays nested three deep across lines with comments and trailing commas, inline tables, bare and quoted keys, `[table]` and repeated `[[array]]` headers, tabs, blank and comment lines, and LF, CRLF or mixed line endings. Both parsers must give the same JSON for them, and `tomllib` must give the value the generator meant. Outside documents add one valid feature that the parser does not read: a float, a hexadecimal, octal or binary integer, a date or time, a multi-line string, a dotted key (also inside an inline table), or a dotted header. `tomllib` must accept them, and the Lean parser must reject them with a "not supported" or "unsupported value" message. Malformed documents add one of 17 kinds of error, such as a duplicate key, a redefined table, a bad escape or integer, a control character in a string or comment, a lone carriage return, Unicode whitespace or invalid UTF-8; both parsers must reject them. Mutants are subset documents with one to three random character edits. For every document, if the Lean parser accepts it then `tomllib` must accept it with the same JSON, and if only `tomllib` accepts it then the Lean error must be one of the "not supported" messages. So the parser may read less than TOML, but it never misreads. Integers outside 64 bits are read exactly, as `tomllib` does, although TOML 1.0 says to reject them. With seed 1 the 10,000 documents agree in 8 seconds on 8 cores, unloaded (8 seconds of CPU), and 836 of the 2,500 mutants are accepted by both. The first run found that the parser accepted control characters other than tab in comments, which TOML forbids: 73 of 4,000 documents failed.
- `test/mtime-faults.sh` breaks trust-base item 5 on purpose and records what Ninja does, as the list of known failure modes in [trust.md](trust.md). It is not a pass/fail test and is not part of `scripts/check.sh`. It builds a five-edge `mise.toml` (plain copies, a `restat` copy, and a copy that sleeps between reading and writing), applies one fault, builds, and classifies the result: *ok*, *hidden* (a product is stale and `ninja -n` has no work), *repaired* (a product is stale, but the next build fixes it) or *loop* (every build has work). The faults that need coarse mtimes run on an HFS+ disk image made with `hdiutil`, which has 1 s mtimes; elsewhere the script skips them. Inside the Nix shell, `nix shell --inputs-from . nixpkgs#libfaketime -c test/mtime-faults.sh` adds the libfaketime fault. It takes 24 seconds and writes its table to `test/out/mtime-faults/report.txt`.

Shell tests write to `test/out/`.

## Continuous integration

GitHub Actions runs two workflows. Every job runs its commands in the flake's dev shell. Linux is the main platform, so jobs run on `ubuntu-latest` (`x86_64-linux`); `macos-latest` (arm64) also runs the priority jobs, which test Ninja conformance, and alone runs the harnesses that need macOS. Each job restores the Nix store with `nix-community/cache-nix-action`, keyed on `flake.nix` and `flake.lock`, and `.lake` with `actions/cache`, keyed on `lean-toolchain`, `lake-manifest.json` and every `.lean` file. The shared setup is `.github/actions/setup`.

`.github/workflows/ci.yml` runs on every pull request and every push to `main`. The `proofs` job runs `scripts/check.sh` once, since the proofs do not depend on the Ninja release. The `ninja` jobs run `test/ninja-matrix.sh --fuzz 150` on each supported release, 1.12.1 (the minimum) and 1.13.2. The `extras` job runs `test/restat-cmp.sh`, `test/wrap-outputs.sh`, `test/stage4-hello.sh`, `test/sugar.sh` and `test/toml-diff.sh 250`. All of these run on Linux, and the 1.13.2 `ninja` job runs on macOS as well. On the first GitHub run (11e7a90), `proofs` took 71 seconds on Linux against 4 minutes 52 seconds on macOS.

`.github/workflows/nightly.yml` runs once a day at 03:17 UTC and on demand (`workflow_dispatch`). On Linux it runs `test/fuzz.sh 500`, `test/stage6-props.sh --order 3`, `test/toml-diff.sh` at its default size, `test/parser-fuzz.sh` for five minutes in each mode in the `fuzz` shell (failing inputs are uploaded as `parser-fuzz-crash`), `test/mutants.sh`, and `test/ninja-matrix.sh` with its default 500 cases on each supported release. macOS repeats `test/fuzz.sh 500` and the matrix on 1.13.2, and runs `test/conf-sandbox.sh` (it needs `sandbox-exec`), `test/conf-depfiles.sh` (the tracer's Linux path is untested) and `test/conf-determinism.sh` (it masks Mach-O fields). It also runs `test/mtime-faults.sh` with libfaketime on macOS, where `hdiutil` gives the HFS+ faults; that job is informational, so it cannot fail the run, and its report is uploaded as the artifact `mtime-faults-report`. In both workflows the first job, `changed`, decides which of the others run, with `.github/scripts/affected.py`. A job runs only when a file it depends on differs between the commit under test and the last commit on which that job succeeded. The script finds that commit in the workflow's run history: on the same branch, then for a pull request on its base branch. A job's dependencies are the toolchain and flake files, the CI setup and the job's own workflow file, the scripts and helpers it runs, and the import closure of the Lean modules behind the Lake targets it builds. The script lists them per job. A job with no earlier success runs. A skipped or failed run does not count, so a failed job runs again on the next commit or night, except `mtime-faults`, which is informational and counts whenever it finished. A matrix job counts only when every entry succeeded. A nightly run started by hand runs every job. GitHub treats a skipped job as passed for a required check. The job writes its decision, with the changed files behind each run, to the run's summary.
