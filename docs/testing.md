# Testing

Run the tests in the Nix shell (`nix develop`, or direnv with `.envrc`), so that they use the Ninja, Python and compiler pinned by `flake.lock`.

- `scripts/check.sh` is the acceptance gate: it builds everything, rejects `sorry` and `admit`, and checks the axioms of every headline theorem. The Lean tests in `test/MiseTest/` are `#guard` checks that run during the build.
- `test/stage3-diff.sh` compares the parser and evaluation models with real Ninja on 100 random manifests, and checks that both reject 17 malformed ones.
- `test/stage4-hello.sh` builds and runs `examples/hello-c`, and checks that the DSL's commands match `ninja -t commands`.
- `test/restat-cmp.sh` tests the `cmp` wrapper on a `restat` edge with two explicit outputs and an implicit one whose name needs quoting. An edit that leaves the outputs the same reruns only that edge and keeps every mtime, and an edit to one output reruns only its dependent. A failing command and a missing output fail the build and leave the old outputs, their mtimes and no `.mise-old` files, and the next build recovers. The commands always write, so the early cutoff comes from the wrapper; with `restat-cmp = false` the test fails at the first cutoff check.
- `test/stage6-props.sh` runs sequences of edits on each example, building after each edit with a random `-j` level. The edit kinds follow a de Bruijn sequence of order 3, so every ordered triple of edit kinds occurs in some sequence; the edits' values are random. `--order 2` covers every pair instead, and `--random N` runs N sequences of random edits. After every build it compares the products with a clean build byte for byte, and checks that `ninja -n` has no work and `ninja -t missingdeps` finds nothing. After a comment-only edit to `config.in` it checks that only the generator ran. Sequences run in parallel, one worker per core by default (`--workers`), and each has its own seed, so the results do not depend on the number of workers. Each manifest is generated once per `cflags` value, and compiles go through ccache (`--no-ccache` turns it off); a cache hit returns the same object a compile would, so a skipped rebuild still leaves a stale product. With seed 1 it ran 96 edits on `hello-c` and 1,500 on `gen-header`, covering all 64 and all 1,000 triples, in 80 seconds on 8 cores with a warm cache, and every check passed. For comparison, `--random 200` takes 65 seconds and covers all 64 and 265 of the 1,000 triples; `--order 2` takes 30 seconds and covers every pair.
- `test/fuzz.sh [N] [SEED]` tests the Ninja model on random graphs. `lake exe fuzzgen` (`test/MiseTest/Fuzz.lean`) generates N graphs, 500 by default, with static, depfile and `restat` rules, implicit inputs and outputs, order-only inputs and edge variables. A depfile edge has one explicit output and up to two implicit ones, so Ninja reads its deps from the first of several outputs. Every edge runs one helper, `test/fz.c`, which hashes what it reads and follows `include` lines for depfile rules; `Fuzz.lean` gives the model the same semantics. On half the `restat` edges the helper itself leaves unchanged outputs alone (`restat-cmp = false`); on the other half it always writes, and the `cmp` wrapper decides. Each graph comes with a sequence of steps. A step makes some edits: change a source, add a comment, add or remove an `include` line, change an edge's command, rewrite a source with the same contents (only its mtime changes), delete a product, delete `.ninja_log` or `.ninja_deps`, remove an edge that nothing reads (its outputs stay on disk), or add an edge, either a new one or one removed earlier. The step then builds in one of three ways: every edge; only some targets (`ninja TARGET...`), which the model predicts by building the edges the targets need; or with one edge's command failing, chosen by `FZ_FAIL`. A failing build runs either under `-k 0`, where Ninja builds everything that does not depend on the failure, or under the default `-k 1`, where Ninja stops. Which edges finish before a stop depends on Ninja's scheduling, so the driver hands them to `fuzzgen expect`, which checks that each was dirty on its turn and read only up-to-date inputs, and recomputes the later steps from that state. The model has no failing commands, so a failed build is modelled as steps of the edges that finished; `Mise/Model/NOTES.md` lists what that leaves out. `test/fuzz.py` replays the steps against real Ninja with `-j` chosen at random from 1, 2, 8 and 64, or from 1 and 2 for a build that stops, since with many jobs in flight Ninja usually finishes every edge that does not depend on the failure. After each build it checks that exactly the model's edges ran, each once, that the runs form a schedule (below), that the failing edge was tried exactly when the model says, that every output the case has had holds the model's contents or is missing when the model says so, and that `ninja -n` has no work (for the targets, after a partial build; not after a failure); after the last step, `ninja -t missingdeps` must find nothing. The run-set check also tests minimality, which a clean-build comparison cannot see. Touching a source, deleting both logs, and partial and failed builds stay within `Reach`, so the theorems cover them. Deleting one log and removing an edge keep `Inv`, though no theorem states it. Deleting a product and adding an edge leave what the theorems cover, so there the harness tests only the model's dirtiness rule. With seed 1 the 500 cases have 3,313 steps and all pass in 63 seconds on 8 cores. Of the 2,813 builds after the first, 1,862 build everything (1,082 rebuild part of the graph, 491 all of it and 289 nothing), 451 build some targets, 230 run under `-k 0` (135 where the failing edge was dirty and tried) and 270 stop at a failure. At cc432f5, before the schedule check and the `cmp` wrapper, 132 of 251 stopped builds tried the failing edge, and 36 of those left unstarted an edge that `-k 0` would have run. The steps hold 608 added edges, 541 removed edges, 501 deleted products, 497 touches, 269 `.ninja_log` and 254 `.ninja_deps` deletions, and 2,378 edits of the earlier kinds; 820 of the 1,246 depfile edges have implicit outputs. Two broken helpers show what the checks catch: one that never keeps a `restat` output fails 99 cases (64 at 59b14fb, before the new steps, and 128 before half the `restat` edges moved to the wrapper), and one whose depfile leaves out included files fails 183 (252 at 59b14fb). A failing case is shrunk: the driver drops steps, edges, edits, inputs, outputs, includes and sources one at a time, turns partial and failed builds into full builds, has `fuzzgen expect` recompute the model's steps, and keeps each change that fails the same check. `--fz PATH` runs a given helper binary in place of `test/fz.c`. With the `restat` mutant, the first three failures (6 to 8 edges and 5 to 11 edits) shrank to 2 edges and 1 edit each, in 76 to 108 trials and 15 to 25 seconds. The result goes to `test/out/fuzz/shrunk/<i>.json`, and `test/fuzz.py test/out/fuzz/shrunk <i>` replays it. `test/fuzz.sh --opts absent` tests a known difference from the model: half the `restat` edges get an unwrapped command (`fz` mode `x`, emitted with `restat-cmp = false`, since the wrapper would turn a missing output into a failure) that leaves out each output whose hash is a multiple of 3, and the model gives such an output the empty contents a missing file reads as. Ninja then reruns those edges in every build, so these cases fail the run-set and `ninja -n` checks by design (40 of 60 with seed 1, all on `ninja -n`). Ninja would also try a failing edge, and finish edges before a stop, that the model finds clean, so under `absent` no build fails. `--missing-ok` allows exactly that difference: an edge with a missing output may also run, and a second build in place of `ninja -n` may run only such edges and must leave the same contents. The schedule check runs on both builds. With it, 60 cases (400 steps) pass in 9 seconds on 8 cores. See `Mise/Model/NOTES.md` for both differences.
- The schedule check in `test/fuzz.py` tests the assumption behind `parallel_equiv`: a parallel run has the effect of its commands in order of start time, each reading its inputs at the start and writing its outputs at the end, and Ninja's ordering makes that sequence a `Sched`. For every run, `fz` logs six `CLOCK_MONOTONIC_RAW` times (entry, first and last input read, first and last write, exit) and the files it read. Check (b) asks that the six times are in that order, so every read of a command comes before its first write. Check (a) asks that every run starts after each edge producing one of its inputs is done, where inputs are explicit, implicit and order-only inputs and the files the run read, so discovered deps count. A producer that ran is done when it exits, and one that did not run is done when its own producers are, the earliest point at which Ninja could find it clean. Check (a) gives the second conjunct of `Sched`, that no edge reads a later edge's outputs, for the edges sorted by start time; the driver also checks all three conjuncts on that order directly, and the first and third (no edge reads its own outputs, outputs are unique) hold for every emitted manifest by `sched_emit`. Because a producer has exited before a reader starts, two runs that overlap in time never read each other's outputs, so with (b) the parallel run has the effect of the sequence. Each command sleeps a random 0 to 20 ms after entry and again before writing (`--delay`, in microseconds, 0 to turn it off), because without the sleep `fz` exits before Ninja has spawned the next command. With seed 1, 985 of the 1,589 builds at `-j` above 1 that ran two or more edges ran edges at the same time, with 2,479 overlapping pairs and at most 4 runs at once, and every check passed; the counts vary between runs with the machine's load. At 59b14fb, before partial and failed builds, 1,197 of 1,854 such builds overlapped in one run, with 2,780 pairs and at most 5 at once, and 1,015 builds with 1,917 pairs in another; with `--delay 0` only 35 builds overlapped; and with `--delay 0`, a helper that logs its entry 1 s early failed 488 cases on check (a), and one that logs its last write before its first read failed all 500 on check (b). A run whose command fails through `FZ_FAIL` logs nothing, so it is a producer that did not run.
- `test/toml-diff.sh [N] [SEED]` compares the `mise.toml` parser with Python's `tomllib`, which reads TOML 1.0. `test/toml_diff.py` writes N random documents of each of four kinds, 2,500 by default, and `lake exe tomljson` (`test/MiseTest/TomlJson.lean`) prints the Lean parser's value tree for each as canonical JSON, the same bytes as Python's `json.dumps(v, sort_keys=True, separators=(",", ":"))`. Subset documents use only what the parser reads: basic strings with every escape, raw and escaped Unicode up to U+10FFFF, literal strings, decimal integers with signs and underscores, booleans, arrays nested three deep across lines with comments and trailing commas, inline tables, bare and quoted keys, `[table]` and repeated `[[array]]` headers, tabs, blank and comment lines, and LF, CRLF or mixed line endings. Both parsers must give the same JSON for them, and `tomllib` must give the value the generator meant. Outside documents add one valid feature that the parser does not read: a float, a hexadecimal, octal or binary integer, a date or time, a multi-line string, a dotted key (also inside an inline table), or a dotted header. `tomllib` must accept them, and the Lean parser must reject them with a "not supported" or "unsupported value" message. Malformed documents add one of 17 kinds of error, such as a duplicate key, a redefined table, a bad escape or integer, a control character in a string or comment, a lone carriage return, Unicode whitespace or invalid UTF-8; both parsers must reject them. Mutants are subset documents with one to three random character edits. For every document, if the Lean parser accepts it then `tomllib` must accept it with the same JSON, and if only `tomllib` accepts it then the Lean error must be one of the "not supported" messages. So the parser may read less than TOML, but it never misreads. Integers outside 64 bits are read exactly, as `tomllib` does, although TOML 1.0 says to reject them. With seed 1 the 10,000 documents agree in 16 seconds on a loaded 8-core machine (8 seconds of CPU), and 836 of the 2,500 mutants are accepted by both. The first run found that the parser accepted control characters other than tab in comments, which TOML forbids: 73 of 4,000 documents failed.
- `test/mtime-faults.sh` breaks trust-base item 5 on purpose and records what Ninja does, as the list of known failure modes in [trust.md](trust.md). It is not a pass/fail test and is not part of `scripts/check.sh`. It builds a five-edge `mise.toml` (plain copies, a `restat` copy, and a copy that sleeps between reading and writing), applies one fault, builds, and classifies the result: *ok*, *hidden* (a product is stale and `ninja -n` has no work), *repaired* (a product is stale, but the next build fixes it) or *loop* (every build has work). The faults that need coarse mtimes run on an HFS+ disk image made with `hdiutil`, which has 1 s mtimes; elsewhere the script skips them. Inside the Nix shell, `nix shell --inputs-from . nixpkgs#libfaketime -c test/mtime-faults.sh` adds the libfaketime fault. It takes 24 seconds and writes its table to `test/out/mtime-faults/report.txt`.

Shell tests write to `test/out/`.
