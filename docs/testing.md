# Testing

Run the tests in the Nix shell (`nix develop`, or direnv with `.envrc`), so that they use the Ninja, Python and compiler pinned by `flake.lock`. Shell tests write to `test/out/`.

## Running the harnesses

`test/harnesses.toml` is the *registry* of every harness and of the continuous integration (CI) jobs that run them. A harness entry gives its command, its flake shell (`default` or `fuzz`), its platforms and the files it depends on. It may also give arguments for a short `quick` run. A job entry lists the harnesses one CI job runs, in order. `test/run` reads the registry:

- `test/run list` prints every harness and job.
- `test/run NAME` runs one harness, and `test/run NAME:quick` runs its short run. Arguments after `--` go to every harness named.
- `test/run ci.KEY` and `test/run nightly.KEY` run the harnesses of one CI job, as CI runs them.
- `test/run deps TARGET` prints the files a harness or job depends on.
- `test/run affected [--all] WORKFLOW` is the CI gate (see [Continuous integration](#continuous-integration)).
- `test/run lint` checks that every job in the workflows is in the registry and calls `test/run`, and that some harness lists every file under `test/` and `fuzz/`.

Each harness runs in its flake shell unless that shell is already active, so `test/run` works from any shell. A harness for another platform is skipped. The run ends with one line per harness, and exits nonzero if any harness failed. Most harnesses take the name of their script; `graph-fuzz` is `test/fuzz.sh`.

## Harnesses

- `scripts/check.sh` is the acceptance gate: it builds everything, rejects `sorry` and `admit`, checks the axioms of every headline theorem, and runs `test/run lint`. The Lean tests in `test/MiseTest/` are `#guard` checks that run during the build.
- `test/stage3-diff.sh` compares the parser and evaluation models with real Ninja on 100 random manifests, and checks that both reject 17 malformed ones.
- **Parser fuzzer.** `fuzz/fuzz.sh parser [--mode text|gen] [--time SECONDS] [--repro FILE...] [-- LIBFUZZER_ARGS]` is a *differential fuzzer* for the parser model, and runs for 60 seconds by default. The registry runs it as `parser-fuzz-text` and `parser-fuzz-gen`, for 300 seconds each. It needs clang with libFuzzer: on Linux it runs in `nix develop .#fuzz`, which `test/run` enters; on macOS the default shell's clang has it. `fuzz/build.sh parser libfuzzer` builds the binary and prints its path, `.lake/build/fuzz/parser-libfuzzer[-asan]/parser`. The binary links Ninja's manifest parser, built from the source of the pinned Ninja (`NINJA_RELEASE` picks the release, 1.13.2 by default), with `fuzz/parser/harness.cc` and the model in `fuzz/MiseFuzz/Parser.lean`.

  When the model's `parse` accepts a manifest, Ninja's `ManifestParser` must accept it too. It must also read the same edges, the same evaluated `command`, `description`, `depfile`, `deps` and `restat` on each non-phony edge, and the same defaults. Inputs the model rejects are not checked, because Ninja accepts more than the subset. Edges whose rule variables form a cycle are not compared, and inputs whose `ninja_required_version` would make Ninja warn or exit are skipped.

  In `text` mode libFuzzer mutates manifest text, starting from 200 manifests of the `difftest` generator and a dictionary of Ninja tokens in `fuzz/parser/parser.dict`. In `gen` mode the input bytes are the *choice sequence* for `genManifest`, so every input is a manifest the model accepts. On an 8-core M1 it tests 11,897 inputs a second in `text` mode and 3,942 in `gen` mode. `--engine afl` builds with AFL++ (American Fuzzy Lop plus plus); it is untested, because nixpkgs has no AFL++ for macOS. *AddressSanitizer* (ASan) is on by default except on macOS, where it hangs at start-up; `MISE_FUZZ_ASAN=1` or `0` overrides the default. Corpora go to `test/out/fuzz-parser-text/corpus` and `test/out/fuzz-parser-gen/corpus`, failing inputs to the `crash` directory beside each, and `--repro FILE...` replays them.

  `Mise/Syntax/NOTES.md` lists the Ninja parsing behaviours the model matches. `pool` and `dyndep` are `parseTimeKeys`, reserved in the DSL so a TOML parameter cannot take either name, and an edge may not list its own outputs as inputs.
- `test/stage4-hello.sh` builds and runs `examples/hello-c`, and checks that the DSL's commands match `ninja -t commands`.
- `test/sugar.sh` tests the `mise.toml` conveniences against real Ninja on a small C program, using `source-globs`, a `foreach` build with depfiles and a link that reads every object through a `%` input. It checks that an alias builds its targets and nothing else, that a header edit rebuilds only its reader, that a new source file is compiled and linked by the next `mise build` and a deleted one is unlinked, and that the DSL's commands match `ninja -t commands`.
- `test/wrap-outputs.sh` tests the command wrapper on an edge without `restat`, with two explicit outputs and an implicit one whose name needs quoting. A command that exits 0 without writing an output fails the build with `mise: out/b.txt was not written`, keeps every old output and its mtime, leaves no `.mise-old` files and runs no dependent; the next build retries the edge. A command that fails after a partial write does the same, and a first build that fails leaves no outputs. With `wrap = false` the same command lets the build succeed and leaves Ninja with work on every later build.
- `test/restat-cmp.sh` tests the wrapper's `cmp` on a `restat` edge with the same outputs. An edit that leaves the outputs the same reruns only that edge and keeps every mtime, and an edit to one output reruns only its dependent. A failing command and a missing output fail the build and keep the old outputs and mtimes. The commands always write, so the early cutoff comes from the wrapper; with `wrap = false` the test fails at the first cutoff check.
- `test/stage6-props.sh` runs sequences of edits on each example, building after each edit with a random `-j` level. The edit kinds follow a de Bruijn sequence of order 3, so every ordered triple of edit kinds occurs; `--order 2` covers every pair instead, and `--random N` runs N sequences of random edits. After every build it compares the products with a clean build byte for byte, and checks that `ninja -n` has no work and `ninja -t missingdeps` finds nothing. After a comment-only edit to `config.in` only the generator may run. Sequences run in parallel, one worker per core by default (`--workers`), each with its own seed. Compiles go through ccache (`--no-ccache` turns it off). With seed 1 the default run passes in 126 seconds on 8 cores with a warm cache; `--order 2` takes 30 seconds.
- `test/fuzz.sh [N] [SEED]` tests the Ninja model on random graphs. `lake exe fuzzgen` (`test/MiseTest/Fuzz.lean`) generates N graphs, 500 by default, with static, depfile and `restat` rules, implicit inputs and outputs, order-only inputs, edge variables and two aliases. Every edge runs one helper, `test/fz.c`, which hashes what it reads and follows `include` lines for depfile rules; `Fuzz.lean` gives the model the same semantics. Edges without `restat` go through the DSL's command wrapper. Half the `restat` edges use `wrap = false` and the helper keeps unchanged outputs itself; on the other half the wrapper's `cmp` decides. `lake exe fuzzgen bytes IN OUT [OPTS]` and `lake exe difftest bytes FILE DIR` generate one case from a byte file.

  Each graph comes with a sequence of steps. A step makes some edits: change a source, add a comment, add or remove an `include` line, change an edge's command, rewrite a source with the same contents, delete a product, delete `.ninja_log` or `.ninja_deps`, remove an edge that nothing reads, add an edge, or *age* a product (set its mtime to one second after the epoch). It then builds every edge, only some targets, or with one edge's command failing (chosen by `FZ_FAIL`). Builds run under `-k 0`, except a build that stops at the failure, which runs under the default `-k 1`. Which edges finish before a stop depends on Ninja's scheduling, so `fuzzgen expect` checks those edges and recomputes the later steps from the state they leave.

  `test/fuzz.py` replays the steps against real Ninja with `-j` chosen at random from 1, 2, 8 and 64 (1 and 2 for a build that stops). After each build it checks that exactly the model's edges ran, each once, that the runs form a schedule (see the schedule check below), that Ninja failed exactly when the model says, that every output holds the model's contents or is missing when the model says so, and that `ninja -n` has no work. After the last step, `ninja -t missingdeps` must find nothing. The run-set check also tests minimality, which a clean-build comparison cannot see.

  Touching a source, deleting both logs, and partial and failed builds stay within `Reach`, so the theorems cover them. Deleting one log and removing an edge keep `Inv`, though no theorem states it. Deleting a product and adding an edge leave what the theorems cover, so for them the harness tests only the model's dirtiness rule. A failed build is modelled through `Mise.Theorems.wrapped_run`; `Mise/Model/NOTES.md` lists what that leaves out. With seed 1 the 500 cases pass in 74 seconds on 8 cores. The harness catches a helper that never keeps a `restat` output and one whose depfile leaves out included files.

  A failing case is shrunk: the driver drops steps, edges, edits, inputs, outputs, includes and sources one at a time, turns partial and failed builds into full builds, and keeps each change that fails the same check. The result goes to `test/out/fuzz/shrunk/<i>.json`, and `test/fuzz.py test/out/fuzz/shrunk <i>` replays it. `--fz PATH` runs a given helper binary in place of `test/fz.c`.

  `test/fuzz.sh --opts absent` tests the wrapper's failure path. A quarter of the edges get a wrapped command (`fz` mode `x`) that leaves out some outputs. The wrapper fails such a run with `mise: OUT was not written` and puts the old outputs back with their mtimes, so in the model the run changes nothing (`natFail` in `Fuzz.lean`). The edge stays dirty, Ninja retries it in the next build, and no edge that reads its outputs runs. Every check applies. With seed 1, 200 cases pass in 25 seconds on 8 cores.

  `--opts absent,nowrap` tests a known difference from the model. Half the `restat` edges get the same command with `wrap = false`, and the model gives a left-out output the empty contents a missing file reads as. Ninja then reruns those edges in every build, so these cases fail the run-set and `ninja -n` checks by design, and no edge is made to fail. Such case files say `"missingOk": true`, which turns on `--missing-ok`: an edge with a missing output may also run, and a second build in place of `ninja -n` may run only such edges and must leave the same contents. With it, 50 cases pass in 10 seconds on 8 cores. With seed 2, 5 of 100 cases fail the run-set check: Ninja skips an edge the model runs, because the edge reads an output its producer left out. The wrapper rules this out. `Mise/Model/NOTES.md` describes both differences.
- **In-process build fuzzer.** `fuzz/fuzz.sh build [--engine libfuzzer|afl|standalone] [--time SECONDS] [--cases N] [--seed S] [--repro FILE...]` builds one binary with `fuzz/build.sh build ENGINE` and runs it; `fuzz/build.sh` alone prints the binary's path, `.lake/build/fuzz/build-ENGINE[-asan]/build`. Both run inside `nix develop .#fuzz`, which adds clang, AFL++ on Linux and `NINJA_SRC`; `test/run build-fuzz` enters it. The binary links the build logic of Ninja 1.13.2 through `fuzz/build/harness.cc` with the model and the case generator of `test/fuzz.sh` (via `fuzz/MiseFuzz/Build.lean`). Commands run against an *in-memory file system* on which no two mtimes tie, while `.ninja_log` and `.ninja_deps` are real files. The front of an input drives the generator, and the back drives the schedule (`-j` for each step and which command in flight finishes next).

  The harness checks what `test/fuzz.py` checks, except the schedule timings and `-t missingdeps`. On a mismatch it writes the case to `test/out/fuzz/inproc/<n>.json` (or `$MISE_FUZZ_OUT`) and aborts, and `test/fuzz.py test/out/fuzz/inproc <n>` replays the case against real Ninja. The standalone engine runs N inputs of 4,096 pseudo-random bytes (`--cases N`, 500 by default, from `--seed S`), and `--repro FILE...` replays files under any engine. On an 8-core M1, `fuzz/fuzz.sh build --engine standalone --cases 500` runs 58 cases a second. The harness does not cover real mtime granularity and ties, real processes, the real `sh` wrapper and `cmp`, overlap in time, `mise gen`, `-t missingdeps`, or sandbox and trace confinement.
- The schedule check in `test/fuzz.py` tests the assumption behind `parallel_equiv`: a parallel run has the effect of its commands in order of start time, each reading its inputs at the start and writing its outputs at the end, and Ninja's ordering makes that sequence a `Sched`. For every run, `fz` logs six `CLOCK_MONOTONIC_RAW` times (entry, first and last input read, first and last write, exit) and the files it read. Check (b) asks that the six times are in that order, so every read comes before the first write. Check (a) asks that every run starts after each producer of one of its inputs is done, counting explicit, implicit and order-only inputs and the files the run read.

  A producer that ran is done when it exits. One that did not run, including one failed through `FZ_FAIL` (which logs nothing), is done when its own producers are. Check (a) gives the second conjunct of `Sched` for the edges sorted by start time, and the driver checks all three conjuncts on that order directly; `sched_emit` proves the first and third for every emitted manifest. Each command sleeps a random 0 to 20 ms after entry and again before writing (`--delay`, in microseconds, 0 to turn it off), since without the sleep `fz` exits before Ninja spawns the next command. With seed 1, 983 of the 1,552 builds at `-j` above 1 that ran two or more edges ran edges at the same time, and every check passed. The check catches a helper that logs its entry early and one that logs a write before its first read.
- `test/mutants.sh [--via real|inproc] [--cases N] [--seed S] [--workers W] [MUTANT...]` checks that the random-graph harness catches a wrong model. Each mutant in `test/mutants.py` is one small edit to a definition in `Mise/Model/Basic.lean`. The script applies it to a copy of the tree in `test/out/mutants/tree` and rebuilds only `fuzzgen`, which imports none of the proofs the mutant breaks.

  For each mutant the script runs the generator twice. The first run keeps the generator's own checks (a second build runs nothing, a depfile edge reads only what it may) and records the first failure. The second turns them off (`FUZZGEN_NO_SELF_CHECK=1`), and `test/fuzz.py --no-shrink` replays its cases against real Ninja and counts the failing cases by check. A failed build counts under `stop` when the model rejects the edges Ninja finished before a stop, and under `tried` when the model and Ninja disagree on whether the failing edge ran. The unmutated model runs first and must pass. The table goes to `test/out/mutants/results.md`. `--cases 40 never-keep trace-reverse` kills both mutants in 42 seconds.

  | Mutant | Change |
  |---|---|
  | `mtime-flip` | output dirty when newer than its newest input |
  | `no-mtime` | drop the output mtime test |
  | `no-logtime` | drop the log time test |
  | `no-cmd` | drop the command test |
  | `all-outs` | edge dirty only when every output is dirty |
  | `restat-mtime` | compare a `restat` output's mtime too |
  | `never-keep` | a `restat` run rewrites every output |
  | `always-keep` | a `restat` run keeps every existing output |
  | `keep-all-rules` | every rule keeps unchanged outputs, not only `restat` |
  | `deps-ignored` | dirtiness ignores the recorded deps |
  | `deps-missing-ok` | a depfile output without a deps entry is not dirty |
  | `deps-stale` | a deps entry, once written, is never updated |
  | `oo-dirty` | order-only inputs count for dirtiness |
  | `log-skip-kept` | no new log entry for a kept output |
  | `log-first-out` | log only the first output |
  | `log-old-time` | log the time before the run, not the run's time |
  | `trace-reverse` | visit the edges in reverse order |
  | `trace-upfront` | decide every edge's dirtiness before running any |
  | `trace-all` | report every visited edge as run |
  | `no-implicit` | drop implicit inputs from the model edge |

  `log-old-time` is equivalent. The log time is used only in the test `lt < newest D`, and no input carries the run's own time `t`, because every time belongs to one write and an edge does not read its own outputs; so `t - 1 < N` holds exactly when `t < N`. The `.ninja_deps` deletion is what kills `deps-missing-ok`, and ageing a product is what kills `no-mtime` and `all-outs`.

  `--via inproc` rebuilds the in-process build fuzzer (`fuzz/build.sh build standalone`) in place of `fuzzgen` and runs the mutants through it with the model's self-checks off (`MISE_FUZZ_NO_SELF_CHECK`). It writes its table to `test/out/mutants-inproc/results.md`, and kills 19 of the 20 mutants in 238 seconds; the survivor is `log-old-time`.
- `test/ninja-matrix.sh [--workers W] [--fuzz N] [--seed S] [RELEASE...]` runs four shell harnesses against several Ninja releases: `stage3-diff.sh`, `stage4-hello.sh`, `stage6-props.sh --order 2` and `fuzz.sh` with N cases (500 by default). With no RELEASE it runs the supported releases, 1.12.1 and 1.13.2. Ninja 1.10.2 and 1.11.1 are unsupported: the script first checks that each refuses an emitted manifest with "incompatible with build file ninja_required_version". `test/ninja-matrix.sh --refuse-only [RELEASE...]` runs only that check, for the named releases (by default the unsupported ones), and exits nonzero if one accepts the manifest or fails with another error. Named explicitly, an unsupported release still runs the harnesses, through a `ninja` shim in `test/out/matrix/<release>/shim/` that lowers the version binding, and is known to fail.

  The flake builds each release from its upstream tag as the package `ninja-1_10_2`, `ninja-1_11_1`, `ninja-1_12_1` or `ninja-1_13_2`. The script runs in the default shell and puts each release first on PATH, so only Ninja changes. `nix develop .#ninja-1_10_2` (and so on) gives a shell with that release for running one harness by hand. Logs go to `test/out/matrix/<release>/`. Ninja 1.10.2 has no `-t missingdeps`, so on it `props.py` and `fuzz.py` skip that check and say so. With seed 1 and 500 fuzz cases on 8 cores, every harness passes on 1.12.1 and 1.13.2, in 264 seconds. The default shell's Ninja is 1.13.2.

  With `--fuzz 50 1.10.2 1.13.2`, 4 of the 50 random-graph cases fail on `ninja -n` on 1.10.2, all after a step that deletes `.ninja_deps`. When a `restat` command keeps its output, Ninja 1.10.2 logs the mtime of the newest input it knew of when the build started. With the deps entry missing, that leaves out the discovered inputs, so a newer discovered input makes the edge dirty in the next build. Ninja 1.11.1 has the same bug, so the minimum is 1.12.1. Ninja 1.12.0 is untested.
- `test/conf-sandbox.sh [N] [SEED]` checks trust-base item 2 on macOS. `test/confine.py` rewrites each `build.ninja` so that every command runs under `sandbox-exec` with its own profile, which kills the command when it reads the contents of a file it may not read or writes a file it may not write. Every command may read the toolchain (the Nix store, system libraries, random devices and a private `TMPDIR`) and its own outputs. In the build directory a static command may also read its explicit and implicit inputs, and a depfile command may read what `Graph.DynOK` allows: any path no edge produces, and its own inputs, order-only ones included. A command may write only its outputs, its depfile, the temporary files clang renames onto its outputs, and its `TMPDIR`.

  The script builds each example through every edit kind of the property harness, 70 commands in all, and then runs the N random-graph cases (500 by default) with `fuzz.py --confine sandbox`. With seed 1 the random graphs pass in 164 seconds on 8 cores. The sandbox kills three broken examples that build without it: a missing implicit input, a missing order-only input and an undeclared depfile. A third build then refuses without killing and traces the refusals, which names the file.

  The sandbox does not confine metadata: a command may `stat` any path and list any directory in the build directory. Commands must be simple commands (no shell operators), since the prefix applies to the first program only. In the DSL's wrapper the prefix goes on the command inside, so the command is confined as it would be alone. The wrapper's `sh` runs outside any sandbox, since a sandboxed process cannot start a second one, and runs only builtins. Each `mv`, `rm` and `cmp` it starts runs under a profile that allows only the toolchain and the edge's outputs and their `OUT.mise-old` copies; that profile refuses without killing, and the harness fails any build whose output shows a refusal. Linux has no `sandbox-exec`, so the script skips there.
- `test/conf-depfiles.sh [N] [SEED]` checks item 3. `test/trace.c` is a shared library that wraps `open`, `openat` and `fopen` and logs every file a process opens; `confine.py` loads it into every command with `DYLD_INSERT_LIBRARIES` (`LD_PRELOAD` on Linux, which is untested). After each build, every file a depfile command read in the build directory must be an explicit or implicit input of its edge or a dependency Ninja recorded from its depfile (`ninja -t deps`), and every command's reads and writes must be ones the sandbox allows. Reads outside the build directory must be in the toolchain; they are not compared with the depfile, since `-MMD` leaves system headers out. Only the command inside the wrapper is traced. A depfile command that fails records no deps, so its reads are checked against the sandbox's rules only. `test/fuzz.sh --opts absent 50 1 -- --confine sandbox` and `-- --confine trace` run the wrapper's failure path confined.

  With seed 1 the 500 random-graph cases pass in 138 seconds. The check catches `gen-header` built with `-isystem build` in place of `-Ibuild`, which makes `build/config.h` a system header that `-MMD` leaves out, and a helper whose depfile drops the last file it read. The tracer misses some reads. macOS strips `DYLD_*` from protected programs (anything in `/bin` or `/usr/bin`), so the check fails a command that ran but left no trace. It does not see reads by the dynamic loader, through raw system calls, by a statically linked program or through an inherited descriptor, and it does not see metadata reads such as `stat`.
- `test/conf-determinism.sh` checks the determinism half of item 2. For each example and each of four `cflags` values it makes two clean builds in different directories, at least a second apart, with `-j1` and `-j8` and with different time zones and locales, and compares the products byte for byte. With `-O2 -Wall`, `-O0` and `-O1 -DMISE_FLAG=1` all 7 products are identical. With `-O0 -g` the objects embed the build directory, and they are identical once one directory's path is substituted for the other. The linked binaries also differ in `LC_UUID` and the ad hoc code signature; with the path substituted and those two zeroed, they are identical. The helper `fz` of the random-graph harness is deterministic by construction, and `fuzz.sh` checks its outputs against the model.
- `test/toml-diff.sh [N] [SEED]` compares the `mise.toml` parser with Python's `tomllib`, which reads TOML 1.0. `test/toml_diff.py` writes N random documents of each of four kinds, 2,500 by default, and `lake exe tomljson` (`test/MiseTest/TomlJson.lean`) prints the Lean parser's value tree for each as canonical JSON. Subset documents use only what the parser reads (strings, decimal integers, booleans, arrays, inline tables, table and array headers, comments and mixed line endings); both parsers must give the same JSON, and the value the generator meant. Outside documents add one valid feature the parser does not read, such as a float, a date or a dotted key; `tomllib` must accept them, and the Lean parser must reject them with a "not supported" or "unsupported value" message. Malformed documents add one of 17 kinds of error, and both parsers must reject them. Mutants are subset documents with one to three random character edits.

  For every document, if the Lean parser accepts it then `tomllib` must accept it with the same JSON, and if only `tomllib` accepts it then the Lean error must be one of the "not supported" messages. The parser may read less than TOML, but it never misreads. Integers outside 64 bits are read exactly, as `tomllib` does, although TOML 1.0 says to reject them. With seed 1 the 10,000 documents agree in 8 seconds on 8 cores.
- `test/mtime-faults.sh` breaks trust-base item 5 on purpose and records what Ninja does, as the list of known failure modes in [trust.md](trust.md). It is not a pass/fail test and is not part of `scripts/check.sh`. It builds a five-edge `mise.toml` (plain copies, a `restat` copy, and a copy that sleeps between reading and writing), applies one fault, builds, and classifies the result: *ok*, *hidden* (a product is stale and `ninja -n` has no work), *repaired* (a product is stale, but the next build fixes it) or *loop* (every build has work). The faults that need coarse mtimes run on an HFS+ disk image made with `hdiutil`, which has 1 s mtimes; elsewhere the script skips them. Inside the Nix shell, `nix shell --inputs-from . nixpkgs#libfaketime -c test/mtime-faults.sh` adds the libfaketime fault. It takes 24 seconds and writes its table to `test/out/mtime-faults/report.txt`.

## Continuous integration

GitHub Actions runs two workflows, each job in the flake's dev shell. Linux is the main platform, so jobs run on `ubuntu-latest` (`x86_64-linux`); `macos-latest` (arm64) also runs the priority jobs, which test Ninja conformance, and alone runs the harnesses that need macOS. The shared setup and caches are in `.github/actions/setup`. The harnesses a job runs come from its `[job.WORKFLOW.KEY]` entry in `test/harnesses.toml`, and its step is `nix develop -c test/run ci.KEY` or `nightly.KEY` (`nix develop .#fuzz` for the parser fuzzer), so the workflow files keep only the runners, matrices and uploads.

`.github/workflows/ci.yml` runs on every pull request and every push to `main`. The `proofs` job runs `scripts/check.sh` once, since the proofs do not depend on the Ninja release. The `ninja` jobs run `test/ninja-matrix.sh --fuzz 150` on each supported release, 1.12.1 and 1.13.2. The `extras` job runs `test/restat-cmp.sh`, `test/wrap-outputs.sh`, `test/sugar.sh` and `test/toml-diff.sh 250`. All of these run on Linux, and the 1.13.2 `ninja` job runs on macOS as well.

`.github/workflows/nightly.yml` runs once a day at 03:17 UTC and on demand (`workflow_dispatch`). On Linux it runs `test/fuzz.sh 500`, `test/stage6-props.sh --order 3`, `test/toml-diff.sh`, `fuzz/fuzz.sh parser` for five minutes in each mode (failing inputs are uploaded as `parser-fuzz-crash`), `test/mutants.sh`, and `test/ninja-matrix.sh` on each supported release. macOS repeats `test/fuzz.sh 500` and the matrix on 1.13.2, and runs `test/conf-sandbox.sh`, `test/conf-depfiles.sh` and `test/conf-determinism.sh`. It also runs `test/mtime-faults.sh` with libfaketime; that job is informational, so it cannot fail the run, and its report is uploaded as the artifact `mtime-faults-report`. A run started by hand runs the jobs its `jobs` input names, space-separated, or every job when the input is empty: `gh workflow run nightly.yml -f jobs=parser-fuzz` runs the parser fuzzer alone.

In both workflows the first job, `changed`, runs `test/run affected` to decide which of the others run. A job runs only when a file it depends on differs between the commit under test and the last commit on which that job succeeded, found in the workflow's run history on the same branch, then for a pull request on its base branch. A job's dependencies are the toolchain, flake and Lake files, `test/run` and its registry, the CI setup and the job's own workflow file, the scripts and helpers its harnesses run, and the import closure of the Lean modules behind the Lake targets they build. The registry lists them per harness. A new harness file goes in a harness's `paths`, and `test/run lint` fails until it is listed. A job with no earlier success, or whose earlier commit cannot be fetched, runs. A skipped or failed run does not count, except for the informational `mtime-faults`, and a matrix job counts only when every entry succeeded. The gate writes its decision as one JSON output, `run`, which maps each job key to whether the job runs, and each job's condition is `fromJSON(needs.changed.outputs.run)['KEY']`. It also writes the decision, with the changed files behind each run, to the run's summary. GitHub treats a skipped job as passed for a required check, so a change that touches none of a job's files never waits on that job.
