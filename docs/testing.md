# Testing

Run the tests in the Nix shell (`nix develop`, or direnv with `.envrc`), so that they use the Ninja, Python and compiler pinned by `flake.lock`.

- `scripts/check.sh` is the acceptance gate: it builds everything, rejects `sorry` and `admit`, and checks the axioms of every headline theorem. The Lean tests in `test/MiseTest/` are `#guard` checks that run during the build.
- `test/stage3-diff.sh` compares the parser and evaluation models with real Ninja on 100 random manifests, and checks that both reject 17 malformed ones.
- `test/stage4-hello.sh` builds and runs `examples/hello-c`, and checks that the DSL's commands match `ninja -t commands`.
- `test/stage6-props.sh` runs sequences of edits on each example, building after each edit with a random `-j` level. The edit kinds follow a de Bruijn sequence of order 3, so every ordered triple of edit kinds occurs in some sequence; the edits' values are random. `--order 2` covers every pair instead, and `--random N` runs N sequences of random edits. After every build it compares the products with a clean build byte for byte, and checks that `ninja -n` has no work and `ninja -t missingdeps` finds nothing. After a comment-only edit to `config.in` it checks that only the generator ran. Sequences run in parallel, one worker per core by default (`--workers`), and each has its own seed, so the results do not depend on the number of workers. Each manifest is generated once per `cflags` value, and compiles go through ccache (`--no-ccache` turns it off); a cache hit returns the same object a compile would, so a skipped rebuild still leaves a stale product. With seed 1 it ran 96 edits on `hello-c` and 1,500 on `gen-header`, covering all 64 and all 1,000 triples, in 80 seconds on 8 cores with a warm cache, and every check passed. For comparison, `--random 200` takes 65 seconds and covers all 64 and 265 of the 1,000 triples; `--order 2` takes 30 seconds and covers every pair.
- `test/fuzz.sh [N] [SEED]` tests the Ninja model on random graphs. `lake exe fuzzgen` (`test/MiseTest/Fuzz.lean`) generates N graphs, 500 by default, with static, depfile and `restat` rules, implicit inputs and outputs, order-only inputs and edge variables. Each graph comes with a sequence of edits: change a source, add a comment, add or remove an `include` line, or change an edge's command. Every edge runs one helper, `test/fz.c`, which hashes what it reads and follows `include` lines for depfile rules; `Fuzz.lean` gives the model the same semantics. The generator runs the model's `buildTrace` on each step and records the edges it runs and the contents it leaves. `test/fuzz.py` replays the steps against real Ninja with `-j` chosen at random from 1, 2, 8 and 64. After each build it checks that exactly the model's edges ran, each once, that the runs form a schedule (below), that every product holds the model's contents, and that `ninja -n` has no work; after the last step, `ninja -t missingdeps` must find nothing. The run-set check also tests minimality, which a clean-build comparison cannot see. With seed 1 the 500 cases have 3,217 steps and all pass in 84 to 104 seconds on 8 cores shared with other jobs. Of the 2,717 steps after the first build, 1,724 rebuild part of the graph, 670 rebuild all of it and 323 rebuild nothing. Two broken helpers show what the checks catch: one that never keeps a `restat` output fails 128 cases, and one whose depfile leaves out included files fails 238. A failing case is shrunk: the driver drops steps, edges, edits, inputs, outputs, includes and sources one at a time, has `fuzzgen expect` recompute the model's steps, and keeps each change that fails the same check. `--fz PATH` runs a given helper binary in place of `test/fz.c`. With the `restat` mutant, the first three failures (6 to 10 edges and 5 to 12 edits) shrank to 2 edges and 1 edit each, in 77 to 133 trials and 10 to 18 seconds. The result goes to `test/out/fuzz/shrunk/<i>.json`, and `test/fuzz.py test/out/fuzz/shrunk <i>` replays it.
- The schedule check in `test/fuzz.py` tests the assumption behind `parallel_equiv`: a parallel run has the effect of its commands in order of start time, each reading its inputs at the start and writing its outputs at the end, and Ninja's ordering makes that sequence a `Sched`. For every run, `fz` logs six `CLOCK_MONOTONIC_RAW` times (entry, first and last input read, first and last write, exit) and the files it read. Check (b) asks that the six times are in that order, so every read of a command comes before its first write. Check (a) asks that every run starts after each edge producing one of its inputs is done, where inputs are explicit, implicit and order-only inputs and the files the run read, so discovered deps count. A producer that ran is done when it exits, and one that did not run is done when its own producers are, the earliest point at which Ninja could find it clean. Check (a) gives the second conjunct of `Sched`, that no edge reads a later edge's outputs, for the edges sorted by start time; the driver also checks all three conjuncts on that order directly, and the first and third (no edge reads its own outputs, outputs are unique) hold for every emitted manifest by `sched_emit`. Because a producer has exited before a reader starts, two runs that overlap in time never read each other's outputs, so with (b) the parallel run has the effect of the sequence. Each command sleeps a random 0 to 20 ms after entry and again before writing (`--delay`, in microseconds, 0 to turn it off), because without the sleep `fz` exits before Ninja has spawned the next command. With seed 1, 974 of the 1,795 builds at `-j` above 1 that ran two or more edges ran edges at the same time, with 1,687 overlapping pairs and at most 5 runs at once, and every check passed; the counts vary between runs with the machine's load (1,072 builds and 2,021 pairs in another run). With `--delay 0` the 500 cases take 44 seconds and only 21 builds overlap. With `--delay 0`, a helper that logs its entry 1 s early fails 486 cases on check (a), and one that logs its last write before its first read fails all 500 on check (b).
- `test/toml-diff.sh [N] [SEED]` compares the `mise.toml` parser with Python's `tomllib`, which reads TOML 1.0. `test/toml_diff.py` writes N random documents of each of four kinds, 2,500 by default, and `lake exe tomljson` (`test/MiseTest/TomlJson.lean`) prints the Lean parser's value tree for each as canonical JSON, the same bytes as Python's `json.dumps(v, sort_keys=True, separators=(",", ":"))`. Subset documents use only what the parser reads: basic strings with every escape, raw and escaped Unicode up to U+10FFFF, literal strings, decimal integers with signs and underscores, booleans, arrays nested three deep across lines with comments and trailing commas, inline tables, bare and quoted keys, `[table]` and repeated `[[array]]` headers, tabs, blank and comment lines, and LF, CRLF or mixed line endings. Both parsers must give the same JSON for them, and `tomllib` must give the value the generator meant. Outside documents add one valid feature that the parser does not read: a float, a hexadecimal, octal or binary integer, a date or time, a multi-line string, a dotted key (also inside an inline table), or a dotted header. `tomllib` must accept them, and the Lean parser must reject them with a "not supported" or "unsupported value" message. Malformed documents add one of 17 kinds of error, such as a duplicate key, a redefined table, a bad escape or integer, a control character in a string or comment, a lone carriage return, Unicode whitespace or invalid UTF-8; both parsers must reject them. Mutants are subset documents with one to three random character edits. For every document, if the Lean parser accepts it then `tomllib` must accept it with the same JSON, and if only `tomllib` accepts it then the Lean error must be one of the "not supported" messages. So the parser may read less than TOML, but it never misreads. Integers outside 64 bits are read exactly, as `tomllib` does, although TOML 1.0 says to reject them. With seed 1 the 10,000 documents agree in 16 seconds on a loaded 8-core machine (8 seconds of CPU), and 836 of the 2,500 mutants are accepted by both. The first run found that the parser accepted control characters other than tab in comments, which TOML forbids: 73 of 4,000 documents failed.

Shell tests write to `test/out/`.
