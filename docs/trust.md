# Trust base

The proofs cover everything from the DSL to the abstract Ninja model, including that the printer emits text the parser model reads back to the emitted syntax tree. Reading `mise.toml` is outside the proofs, but its result must pass the same validity check as a description written with the Lean DSL, so a decoding mistake gives a wrong build, never an unsound one. `test/toml-diff.sh` checks the TOML parser against Python's `tomllib`. The following are assumed, and the tests in [testing.md](testing.md) check most of them.

1. Real Ninja implements the model and the parser model for the supported subset. `test/fuzz.sh` checks the model on random graphs, with full, partial and failed builds: real Ninja must run the same edges and leave the same contents.
2. Commands are deterministic and read only declared or discovered inputs. For depfile commands this is the hypothesis `Graph.DynOK`; `ninja -t missingdeps` checks it.
3. Depfiles list every file the command read.
4. Every command writes or keeps each of its outputs, and a `restat` command leaves an output untouched only when its contents would not change (`Sem.keep_eq`). Ninja reruns an edge with a missing output in every build, so a command that leaves one out still gives correct contents, but a second build is not empty. By default the DSL wraps every `restat` command in a script that compares old and new outputs with `cmp` ([usage.md](usage.md)), and then this item reduces to the script, `cmp` and `mv` behaving as `Mise.Model.wrapRun` models them. `wrapRun_kept_iff` shows the modelled script keeps an output exactly when the command wrote the old contents again, and `run_withCmp` shows that the Ninja model's `restat` run under `Sem.withCmp` is that script. A wrapped command that leaves out an output fails instead of leaving it missing, and the script puts the old outputs back (`wrapRun_fail`). `test/restat-cmp.sh` and `test/fuzz.sh` test the script against real Ninja. For a rule with `restat-cmp = false`, and for a command without `restat`, the item remains an assumption about the command.
5. Mtimes are faithful: no clock skew, nothing edits files during a build, and each command reads its inputs at the start and writes its outputs at the end. `test/fuzz.py` checks the last part for its helper and that Ninja starts a command only after its producers exit. Ninja 1.13 logs each command's start time, taken from the filesystem, and treats an output as dirty when an input is newer than that time. `test/mtime-faults.sh` breaks the assumption on purpose; these are the failure modes it found with Ninja 1.13.2 on macOS:
   - An edit in the same mtime tick as the start of a command that read the old contents leaves stale products that no later build repairs. On HFS+, with 1 s mtimes, editing a source within the second of the build that read it is enough. On APFS the tick is 1 ns, and the script has to stamp the edit with the logged start time.
   - A source mtime set backwards leaves stale products that no later build repairs. Both `touch -t 200001010000` and restoring an older copy with `cp -p` do this, as would `tar` or `rsync -t`.
   - An edit during a build, after the command read the file, leaves a stale product, and the build still succeeds. The next build repairs it, because the edit is newer than the logged start time. On HFS+, an edit in the same second as the command's start is never repaired.
   - A source stamped by a clock behind the build directory's (another host's files copied with their mtimes, or a network filesystem with a slow server clock) leaves stale products, as a backwards mtime does. A source stamped one hour ahead makes every build rerun its readers until the clock catches up, so `ninja -n` always has work. Outputs stamped one hour ahead do no harm, since Ninja compares inputs with the logged start time.
   - libfaketime works on macOS from nixpkgs (`date` under `faketime -f '+1h'` is 3,600 s ahead), but faking Ninja's clock changes nothing: a build under `+1h`, an edit, and a build under `-1h` give correct products. Ninja takes start times from the filesystem, and the kernel stamps mtimes.

The supported subset is top-level bindings, `rule`, `build` with implicit outputs and implicit and order-only inputs, edge bindings, and `default`, with the rule keys listed in `Mise/Syntax/NOTES.md`. Out of scope: `dyndep`, `generator`, `pool`, `subninja`, `include`, MSVC deps, response files and Windows.
