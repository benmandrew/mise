# Trust base

The proofs cover everything from the DSL to the abstract Ninja model, including that the printer emits text the parser model reads back to the emitted syntax tree. Reading `mise.toml` is outside the proofs, but its result must pass the same validity check as a description written with the Lean DSL, so a decoding mistake gives a wrong build, never an unsound one. The conveniences (`source-globs`, `foreach`, `%` inputs, sorting the builds and flattening aliases) expand before the check, so the same holds for them. `test/toml-diff.sh` checks the TOML parser against Python's `tomllib`. The following are assumed, and the tests in [testing.md](testing.md) check most of them.

1. Real Ninja implements the model and the parser model for the supported subset. `test/fuzz.sh` checks the model on random graphs, with full, partial and failed builds: real Ninja must run the same edges and leave the same contents. Every emitted manifest starts with `ninja_required_version = 1.12.1`, so releases older than 1.12.1 refuse it. `test/ninja-matrix.sh` checks the model against 1.12.1 and 1.13.2, each built from its upstream tag, and checks that 1.10.2 and 1.11.1 refuse the manifest. Those two disagree with the model after `.ninja_deps` is deleted, as the random-graph harness does: a `restat` depfile edge that keeps its output logs an mtime older than a discovered input, so the next build reruns it ([testing.md](testing.md)). Its contents stay correct, but `ninja -n` is not empty. Ninja 1.12.0 and releases after 1.13.2 are untested. The model leaves out `phony` edges. The DSL emits one per alias, with at least one input and an output that no edge reads, so this item also assumes that Ninja runs no command for such an edge and builds its inputs when asked for its output. The random-graph harness gives every case two aliases and asks for them in partial builds.
2. Commands are deterministic and read only declared or discovered inputs. For depfile commands this is the hypothesis `Graph.DynOK`; `ninja -t missingdeps` checks it. `test/conf-sandbox.sh` runs every command of the examples and the random-graph harness under a macOS sandbox that kills it on a read outside its inputs (for depfile commands, outside what `Graph.DynOK` allows) and the toolchain, or a write outside its outputs. A command in the DSL's wrapper is confined as it would be alone, and the wrapper's `mv`, `rm` and `cmp` may read and write only the edge's outputs and their `OUT.mise-old` copies in the build directory. The wrapper's `sh` runs only builtins, and runs unconfined, since macOS cannot start a sandbox inside another ([testing.md](testing.md) gives the details). `test/conf-determinism.sh` checks that clean builds in different directories and at different times give identical products.
3. Depfiles list every file the command read. `test/conf-depfiles.sh` traces the files each command opens and checks that each depfile command read in the build directory only its inputs and the dependencies Ninja recorded from its depfile. System headers are outside this check, since `-MMD` leaves them out; they are assumed fixed with the toolchain.
4. A command that exits 0 writes every output, a command that fails changes no file, and a `restat` command leaves an output untouched only when its contents would not change (`Sem.keep_eq`). The model has no failing commands, and its `St.run` writes every output of every edge. Ninja reruns an edge with a missing output in every build, so a command that exits 0 without writing an output still gives correct contents, but a second build is not empty and `rebuild_noop` fails. By default the DSL wraps every command in a script that ensures this item ([usage.md](usage.md)). The item then reduces to the script, `cmp`, `mv` and `rm` behaving as `Mise.Model.script` models them, and to no file called `OUTPUT.mise-old` existing outside the script. `script_fail`, `script_ok`, `wrapRun_kept_iff` and `run_withCmp` ([theorems.md](theorems.md)) show that the script meets the item and is the Ninja model's run under `Sem.withCmp`. `Mise.Theorems.wrapped_run` shows that a failed run leaves the state as it was, so every reachable-state theorem covers histories with failed commands. `test/wrap-outputs.sh`, `test/restat-cmp.sh` and `test/fuzz.sh` test the script against real Ninja, and `test/fuzz.sh --opts absent` tests its failure path on random graphs with commands that leave out outputs. For a rule with `wrap = false` the item remains an assumption about the command.
5. Mtimes are faithful: no clock skew, nothing edits files during a build, and each command reads its inputs at the start and writes its outputs at the end. `test/fuzz.py` checks the last part for its helper, and checks that Ninja starts a command only after its producers exit. Ninja 1.13 logs each command's start time, taken from the filesystem, and treats an output as dirty when an input is newer than that time. `test/mtime-faults.sh` breaks the assumption on purpose. With Ninja 1.13.2 on macOS it found these failure modes:
   - An edit in the same mtime tick as the start of a command that read the old contents leaves stale products that no later build repairs. On HFS+, with 1 s mtimes, editing a source within the second of the build that read it is enough. On APFS the tick is 1 ns, and the script has to stamp the edit with the logged start time.
   - A source mtime set backwards leaves stale products that no later build repairs. Both `touch -t 200001010000` and restoring an older copy with `cp -p` do this, as would `tar` or `rsync -t`.
   - An edit during a build, after the command read the file, leaves a stale product, and the build still succeeds. The next build repairs it, because the edit is newer than the logged start time. On HFS+, an edit in the same second as the command's start is never repaired.
   - A source stamped by a clock behind the build directory's (another host's files copied with their mtimes, or a network filesystem with a slow server clock) leaves stale products, as a backwards mtime does. A source stamped one hour ahead makes every build rerun its readers until the clock catches up, so `ninja -n` always has work. Outputs stamped one hour ahead do no harm, since Ninja compares inputs with the logged start time.
   - libfaketime works on macOS from nixpkgs (`date` under `faketime -f '+1h'` is 3,600 s ahead), but faking Ninja's clock changes nothing: a build under `+1h`, an edit, and a build under `-1h` give correct products. Ninja takes start times from the filesystem, and the kernel stamps mtimes.

The theorems fix one graph. Editing `mise.toml`, or adding or removing a file that a `source-globs` pattern matches, changes the graph between builds. No theorem covers a history across that change, since `Reach` is defined for one list of edges. The random-graph harness tests such histories with edges added and removed, against the model's dirtiness rule only.

The supported subset is top-level bindings, `rule`, `build` with implicit outputs and implicit and order-only inputs, edge bindings, `phony` edges for aliases, and `default`, with the rule keys in `ruleKeys` (`Mise/Syntax/Ast.lean`). Out of scope: `dyndep`, `generator`, `pool`, `subninja`, `include`, MSVC deps, response files and Windows.
